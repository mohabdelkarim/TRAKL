Μέρος 1: CI/CD Workflows — Επεξήγηση όλων των tools

Το project έχει 13 CI workflows που καλύπτουν code quality, security scanning, secret detection, dependency review, και SBOM. Για ένα solo private project, αυτό είναι περισσότερο από όσο χρειάζεται, αλλά δείχνει ωριμότητα.

Code Quality (3 workflows)

1. Knip — Dead Code Detection

Βρίσκει άχρηστο κώδικα: exports που δεν τα χρησιμοποιεί κανένα αρχείο, dependencies στο package.json που δεν τα χρειάζεται, αρχεία που δεν importάρονται. Τρέχει npx knip --reporter json και ανεβάζει τα αποτελέσματα ως artifact.

Γιατί υπάρχει: Σε ένα project που εξελίσσεται, μένουν "ορφανά" κομμάτια κώδικα. Το Knip τα εντοπίζει πριν γίνουν tech debt.

2. jscpd — Duplicate Code

Σκανάρει τον κώδικα για copy-paste duplication — blocks κώδικα που είναι πανομοιότυπα ή σχεδόν πανομοιότυπα. Παράγει HTML και JSON report.

Γιατί υπάρχει: Αν το ίδιο 50-line block εμφανίζεται σε 3 αρχεία, είναι signal ότι χρειάζεται extraction σε κοινή συνάρτηση.

3. ast-grep — Structural Lint

Linting σε επίπεδο AST (Abstract Syntax Tree) — όχι γραμμή-γραμμή όπως το ESLint, αλλά δομικά. Μπορεί να βρει π.χ. "κάθε useEffect που δεν έχει cleanup function".

Γιατί υπάρχει: Πιάνει patterns που το ESLint/oxlint δεν μπορεί γιατί λειτουργεί σε δομικό επίπεδο, όχι textual.

Security (7 workflows)

4. Semgrep SAST

Static Application Security Testing — σκανάρει τον κώδικα για ευπάθειες χωρίς να τον εκτελεί. Τρέχει με 4 rule packs: p/react-native, p/typescript, p/owasp-top-ten, p/security-audit, και custom rules στο .semgrep.yml. Ανεβάζει αποτελέσματα ως SARIF στο GitHub Security tab.

Τι ψάχνει: eval() με user input, hardcoded secrets, SQL injection patterns, unsafe regex, κλπ.

5. Trivy

All-in-one scanner που ψάχνει για τρία πράγματα ταυτόχρονα: CVEs σε npm dependencies (μέσω package-lock.json), secrets (API keys, tokens), και misconfigurations (Dockerfile, Kubernetes, IaC). Φιλτράρει σε CRITICAL/HIGH/MEDIUM severity, αγνοεί unfixed vulnerabilities. Το exit-code: '0' σημαίνει ότι δεν σπάει το build — μόνο αναφέρει.

6. OSV-Scanner

Open Source Vulnerability scanner από το Google. Εξειδικεύεται σε dependency vulnerabilities — ελέγχει κάθε package στο package.json/package-lock.json ενάντια στην OSV database.

7. Retire.js

Βρίσκει γνωστά vulnerable JS libraries. Παρόμοιο με το OSV-Scanner αλλά εστιάζει σε JS-specific vulnerabilities.

8. Grype

Container/dependency vulnerability scanner από το Anchore. Σκανάρει το filesystem για packages με γνωστά CVEs. Συμπληρώνει το Trivy και OSV-Scanner με διαφορετική database.

9. KICS

Infrastructure as Code security scanner — ψάχνει misconfigurations σε Dockerfile, Kubernetes manifests, Terraform. Στο TRAKL κυρίως για το Dockerfile και τα CI workflows.

10. Checkov

Παρόμοιο με το KICS — IaC security scanning. Διπλή κάλυψη με KICS για misconfigurations σε infrastructure files.

11. TruffleHog

Secret scanner — σκανάρει όλο το git history (με fetch-depth: 0) για leaked API keys, tokens, passwords. Χρησιμοποιεί verification — δεν βρίσκει μόνο patterns, αλλά επιβεβαιώνει αν ένα secret είναι ενεργό.

Supply Chain (2 workflows)

12. Dependency Review

Τρέχει μόνο σε PRs. Ελέγχει τα νέα dependencies που προστίθενται σε ένα PR ενάντια στο GitHub Advisory Database. Αν ένα νέο package έχει vulnerability severity ≥ moderate, σπάζει το build και γράφει comment στο PR.

13. SBOM (Syft)

Software Bill of Materials — παράγει μια πλήρη λίστα όλων των dependencies (direct + transitive) με τις εκδόσεις τους. Για compliance — αν βγει ένα νέο CVE, ξέρεις ακριβώς αν το project το χρησιμοποιεί.

Μέρος 2: Τι θα έκανε ένα Senior Engineer

1. Fix το Transactions Plaintext Leak ΚΡΙΣΙΜΟ

Τα transactions γράφονταν δύο φορές: στο expo-secure-store (encrypted) και στο plaintext AsyncStorage via το partialize του Zustand persist.

Τι θα έκανε ένα senior: Θα αφαιρούσε τα transactions από το partialize εντελώς. Τα transactions πρέπει να ζουν μόνο στο SecureStore. Θα πρόσθετε και ένα test που επιβεβαιώνει ότι το persisted blob δεν περιέχει transactions.

2. Split το Store σε Slices

Το store.ts ήταν 818 γραμμές με ~60 actions. Ένας senior θα το έσπαζε με το Zustand slice pattern: finance, habits, tasks, goals, planner, health, custom, notifications, settings. Κάθε slice έχει τα δικά του state + actions.

Οφέλη: Κάθε slice < 100 γραμμές, πιο εύκολο να βρεις τι ψάχνεις, πιο εύκολο να τεστάρεις isolated.

3. Αλλαγή ID Generation

Το Math.random().toString(36).slice(2, 10) δεν είναι collision-safe ούτε crypto-secure.

Τι θα έκανε ένα senior: crypto.randomUUID() με fallback σε crypto.getRandomValues (UUID v4 manual formatting).

4. Restructure τα Tests — Προσθήκη Missing Coverage

Τα τωρινά tests ήταν επιφανειακά σε κρίσιμα σημεία. Ένας senior θα πρόσθετε: real persistence test, migration tests, SecureStorage integration test, stats edge cases, achievement computation για κάθε achievement.

5. Σταματήσει το Migration Tech Debt

135 γραμμές hand-written migration που χειρίζεται 11 versions. Κάθε νέο field σημαίνει άλλο ένα if (!Array.isArray(record.X)) block.

Τι θα έκανε ένα senior: Δομημένο migration με versioned steps — κάθε migration είναι isolated, testable, idempotent.

6. Μειώσει τα CI Workflows στα Απαραίτητα

13 workflows για solo private project. Ένας senior θα κρατούσε 5: Typecheck+Lint+Test, Semgrep SAST, OSV-Scanner, TruffleHog, Dependency Review.

7. Προσθήκη Error Boundaries στα Tracker Screens

Υπήρχε root ErrorBoundary αλλά κανένα tracker screen δεν είχε το δικό του. Αν το Finance screen crashάρει, ο χρήστης χάνει πρόσβαση σε όλα τα tabs.

8. Typed Safe Navigation

Τα routes είναι hardcoded strings. Αν αλλάξει η δομή των routes, το TypeScript δεν θα πιάσει το mismatch.

9. Προσθήκη E2E Tests

Κανένα E2E test δεν υπάρχει. Ένας senior θα πρόσθετε ένα smoke test με Maestro.

10. Documentation — ADRs

Καμία αρχιτεκτονική απόφαση δεν είναι τεκμηριωμένη. Ένας senior θα πρόσθετε docs/adr/ με ADRs για κάθε σημαντική απόφαση.

Μέρος 4: Τι λείπει ακόμα για Senior-Level

Α. Performance & Architecture

1. Fix το useTrakl() χωρίς selector ΚΡΙΣΙΜΟ

Στο trackers.tsx:61: const store = useTrakl(); — εγγράφει σε όλο το store. Το component re-renderάρει σε κάθε single state change. Και στο profile.tsx:173-202 υπάρχουν 30 ξεχωριστά useTrakl((s) => s.X) calls.

Λύση: Χρησιμοποίησε useShallow από zustand/react/shallow για ένα call με shallow comparison.

2. stats.ts είναι 983 γραμμές — God module

~40 exported functions: finance stats, habit streaks, task grouping, sleep, mood, water, weight, meditation, life score, task sorting.

Λύση: Split σε domain-specific modules: finance.ts, habits.ts, tasks.ts, sleep.ts, health.ts, lifeScore.ts, dates.ts, index.ts.

3. Κανένα useMemo/useCallback στα screens

Μηδέν useMemo ή useCallback σε ολόκληρο το app/ directory. Κάθε render υπολογίζει πάντα τα stats από την αρχή.

4. bestStreak — O(n×60) loop σε κάθε render

Για κάθε habit, 60 iterations × Object.entries(). Με 10 habits = 600 iterations ανά render. Και habitStreak κάνει 365 iterations per habit.

Λύση: Cache το streak στο store ή memoize το αποτέλεσμα.

5. monthExpenses / monthIncome — duplicate iteration

monthNet κάνει δύο full iterations. budgetLeft καλεί monthExpenses ξεχωριστά. Σε ένα screen = 4 iterations του ίδιου array.

Λύση: Single-pass monthSummary function.

6. Split το settingsSlice further

200 γραμμές — το μεγαλύτερο slice. Χειρίζεται onboarding, sample data, backup/restore, tracker toggles, profile, notifications, retention, reset.

Λύση: Split σε onboardingSlice.ts, backupSlice.ts, preferencesSlice.ts.

Β. Security & Data Integrity

7. importAppData rollback αν αποτύχει το secure storage ΚΡΙΣΙΜΟ

Αν το saveTransactionsSecure αποτύχει μετά το set(), το in-memory state έχει τα transactions αλλά το secure storage όχι. Στο επόμενο app launch, τα transactions θα χαθούν.

Λύση: await saveTransactionsSecure() πριν το set(), με try/catch και rollback.

8. as unknown as casts — 3 σημεία

Βρέθηκαν 3 as unknown as casts στον κώδικα:

  • backup.ts:173 — parsed as unknown as BackupData (documented, has oxlint disable). Ελέγχει ότι τα keys υπάρχουν αλλά όχι ότι τα values έχουν το σωστό type
  • i18n.ts:19 — i18n module type bridge (justified, require() returns any)
  • haptics.ts:25 — require('expo-haptics') as unknown as HapticsModule (justified, require() returns any)

Λύση: Για το backup.ts, πρόσθεσε runtime validation με zod ή type guards για τα critical fields. Τα άλλα 2 είναι justified.

Γ. UI & UX

9. testID props για E2E tests

Το Maestro smoke test χρησιμοποιεί text: ".*Trackers.*" — brittle. Αν αλλάξει το i18n string, το test σπάει.

Λύση: Πρόσθεσε testID στα κρίσιμα στοιχεία.

10. ScreenErrorBoundary — hardcoded colors

backgroundColor: '#007AFF' — δεν ακολουθεί το theme. Το app έχει useColors() theme system.

11. Accessibility labels

Κανένα accessibilityRole, accessibilityLabel, accessibilityHint. Η Apple μπορεί να απορρίψει το app για inadequate accessibility.

Δ. DevOps & Process

12. Pre-commit hooks

Δεν υπάρχει husky/lefthook. Τα CI workflows πιάνουν lint/typecheck αλλά μετά το commit.

13. Native crash reporting

PostHog τρέχει μόνο σε web. Σε native δεν υπάρχει κανένα crash reporting. Αν το app crashάρει σε production, δεν το μαθαίνεις ποτέ.

Λύση: Sentry (ή PostHog native) για iOS/Android.

14. Bundle size analysis

Κανένα tool για να μετράς το bundle size.

Ε. Bugs & Cleanup

15. defaultProfile — hardcoded values

  • name: 'Alex' — hardcoded demo name. Ένας νέος user βλέπει "Alex" πριν κάνει onboarding
  • memberSince: new Date(new Date().getFullYear(), 0, 12).toISOString() — 12 Ιανουαρίου χωρίς εξήγηση. Ένας νέος user βλέπει μέλος από 12 Ιανουαρίου αντί για σήμερα
  • language: 'English' — hardcoded αντί για device locale detection

Λύση: memberSince: new Date().toISOString() ή undefined (set στο completeOnboarding). name: '' ή undefined. language από expo-localization.

Μέρος 5: Τι πρέπει να ξέρεις για να φτιάξεις ένα app σαν το TRAKL

1. Θεμέλια — Programming & TypeScript

TypeScript

  • Types vs Interfaces: Πότε χρησιμοποιείς τι
  • Generics: StateCreator<TraklState, [], [], FinanceSlice>
  • Utility types: Omit, Partial, Record
  • Discriminated unions: type ParseResult = { ok: true; data } | { ok: false; error }
  • Type narrowing: if (typeof value === 'object' && value !== null)
  • Strict mode: noUncheckedIndexedAccess, strictNullChecks

JavaScript Fundamentals

  • Immutability: [...s.habits, newHabit] — ποτέ push
  • Array methods: filter, map, reduce, flatMap, some, every
  • Optional chaining: state?.transactions?.[0]?.amount
  • Nullish coalescing: i18n.resolvedLanguage ?? i18n.language ?? 'en'
  • Date handling: Timezone issues, ISO strings, toLocaleDateString()

Functional Programming

  • Pure functions: Ίδια input → ίδια output, no side effects
  • Higher-order functions: useTrakl((s) => s.habits)
  • Currying: i18n.getFixedT(lng)(key)

2. React & React Native

React Core

  • Component lifecycle: mount → update → unmount
  • Hooks rules: Ποτέ hooks μέσα σε conditions/loops
  • useState, useEffect, useRef, useMemo, useCallback
  • Reconciliation: Πώς αποφασίζει React ποια components να re-renderάρει
  • Error boundaries: Class components, getDerivedStateFromError
  • Context API: Μοιρασία state χωρίς prop drilling

React Native Specifics

  • Core components: View, Text, ScrollView, FlatList, TouchableOpacity
  • StyleSheet: Δεν έχει cascade/inheritance (εκτός Text)
  • Platform differences: iOS vs Android — SafeArea, shadows, fonts
  • Native modules: expo-haptics, expo-secure-store, expo-notifications
  • Performance: FlatList vs ScrollView, removeClippedSubviews
  • Bundle size: Hermes engine, tree shaking

Expo Ecosystem

  • Expo SDK: Versioning, upgrade process
  • expo-router: File-based routing, _layout.tsx, (tabs) groups, [id]
  • expo-secure-store: Keychain/Keystore, size limits (~2KB)
  • expo-linear-gradient, expo-haptics, expo-notifications
  • EAS Build: eas.json, build profiles, cloud builds
  • app.config.ts: Dynamic config με plugins, permissions
  • Expo Go vs Dev Client: Πότε χρειάζεσαι custom native code

3. State Management — Zustand

  • create<T>(): Δημιουργία store
  • Selectors: useTrakl((s) => s.habits) — subscribes μόνο στο habits
  • persist middleware: createJSONStorage, partialize, onRehydrateStorage, version, migrate
  • Slice pattern: createFinanceSlice, composition με ...createXSlice(...a)
  • useShallow: Shallow comparison για multiple selectors
  • Outside React: useTrakl.getState() και useTrakl.setState()

4. Architecture & Design Patterns

Layered Architecture

src/
  domain/          — Pure types, no dependencies
  application/     — Business logic, state, hooks
  infrastructure/  — Native integrations, storage, services
  shared/          — Utils, theme, fonts

Rule: Dependencies πάντα προς τα μέσα. Το domain δεν importάρει τίποτα.

Patterns

  • Repository: secureStorage.ts abstracts Keychain/Keystore
  • Factory: createFinanceSlice(...a)
  • Strategy: shareBackup
  • Observer: Zustand subscriptions
  • HOC: withErrorBoundary(Component, screenName)
  • Adapter: AdBanner.tsx vs AdBanner.web.tsx

5. Security

  • expo-secure-store: Keychain (iOS) / Keystore (Android) — encrypted at rest
  • AsyncStorage: Plaintext — ποτέ sensitive data
  • partialize exclusion: Τι μπαίνει σε plaintext vs encrypted
  • Input clamping: Math.min(10_000_000, Math.max(0.01, tx.amount))
  • GDPR consent management: UMP SDK
  • Security scanning: SAST, dependency scanning, secret scanning, IaC scanning

6. Persistence & Data Management

  • AsyncStorage: Plaintext, ~6MB, JSON serialization
  • Secure Storage: ~2KB per key, sync vs async per platform
  • Migrations: Versioned schema, idempotent steps, backfilling, error handling
  • Backup/Restore: Versioning, validation, secure restore, cross-platform sharing

7. Internationalization (i18n)

  • i18next: Namespace organization, RTL support, language detection
  • 20+ γλώσσες: Κάθε string πρέπει να μεταφραστεί
  • Date/number formatting: Διαφορετικό per locale
  • Text length: Γερμανικά είναι 30% πιο μακριά από Αγγλικά

8. Navigation — Expo Router

  • File-based routing: _layout.tsx, (tabs), [id], +not-found.tsx
  • Auth gate: if (!onboarded) redirect('/onboarding')
  • Modal presentation: presentation: 'modal'

9. Styling & UI

  • Design system: useColors(), InterText, Card, ProgressRing

  • GitHub Actions: Triggers, jobs vs steps, matrix builds, caching, artifacts

  • Code quality: oxlint, oxfmt, Knip, jscpd, ast-grep
  • EAS Build & Submit: Cloud builds, App Store / Play Store submission

12. Performance

13. Platform Knowledge

14. Soft Skills & Process

Μέρος 7: Προστασία από Cloning

Πραγματικότητα

Αν το app είναι ήδη στο Play Store/App Store, κάποιος μπορεί ήδη να το κλωνοποιήσει από το binary. Το να κάνεις τον κώδικα public δεν αλλάζει αυτό το risk.

1. License — Το πιο σημαντικό

LicenseForkΠουλάειOpen sourceΣύσταση
MIT✅✅❌ Όχι❌ Πολύ επιτρεπτικό
Apache 2.0✅✅❌ Όχι⚠️ Επιτρεπτικό + patent
GPL-3.0✅✅✅ Ίδιο license✅ Copyleft

Σύσταση: GPL-3.0 ή AGPL-3.0
Αν κάποιος forkάρει και το δημοσιεύσει: Πρέπει να χρησιμοποιήσει ίδιο license, να δημοσιεύσει τον κώδικά του, να συμπεριλάβει το copyright notice σου, και δεν μπορεί να το κλείσει σε proprietary app.

Dual license (μέγιστη προστασία): GPLv3 για open source + commercial license για proprietary use (πληρωμένο).

2. Trademark — Προστάτευσε το όνομα

Το όνομα "TRAKL" δεν προστατεύεται από license. Πρέπει να καταχώρησεις trademark. Χωρίς trademark, κάποιος μπορεί να το ονομάσει "TRAKL Pro" και να το πουλάει.

3. Technical Deterrents

App signature verification

import * as Application from 'expo-application';

if (Platform.OS === 'android' && Application.androidId !== EXPECTED_ANDROID_PACKAGE) {
  // Someone repackaged the app — disable ads or show watermark
}

Δεν είναι真正的 protection — αλλά δυσκολεύει lazy cloners.

AdMob package ID check

Αν κάποιος αλλάξει το package ID και χρησιμοποιήσει τα δικά σου AdMob IDs, η Google θα απορρίψει τα ad requests.

4. GitHub Settings

  • Disable forks (optional): Settings → General → Features → ❌ Allow forking
  • Αν αφήσεις forks, το GPL-3.0 εξασφαλίζει ότι κάθε fork πρέπει να είναι επίσης GPL-3.0

5. Τι ΔΕΝ μπορείς να προστατεύσεις

ΣενάριοΜπορείς να το σταματήσεις;
Κλωνοποίηση και πώληση στο Play Store✅ Ναι — DMCA takedown + trademark
Κλωνοποίηση και πώληση εκτός stores (APK sideload)❌ Όχι practically
Παίρνει 1-2 functions⚠️ Δύσκολο να το αποδείξεις

Η πραγματική απάντηση

Οι cloners είναι lazy. Αν κάποιος είναι αρκετά ικανός να καταλάβει την αρχιτεκτονική, να αλλάξει το branding, να βγάλει το license, και να το δημοσιεύσει στα stores — ττε είναι αρκετά ικανός να γράψει το δικό του app από την αρχή.
